# پچ ۶۰-ج — اصلاح نقش اشتباه + تغییر نقش در همان صفحهٔ دسترسی‌ها

> تاریخ: 2026-11-22 · علامت: کاربر صندوق‌دار همهٔ منوها را می‌بیند و به حسابداری هم وارد می‌شود
> علت: نقشِ آن کاربر در جدول «مالک (owner)» است — مالک به‌طراحی سلب‌ناپذیر است و
> تیک‌های صفحهٔ دسترسی‌ها روی مالک اثری ندارند؛ لیست خالیِ مالک یعنی همهٔ ۲۷ ماژول.

## مرحلهٔ ۱ — SQL (فوری؛ بدون دیپلوی)

`patch-60c-role-fix.sql` را در Supabase → SQL Editor بخش‌به‌بخش Run کن:

- **بخش ۱**: وضعیت واقعی همهٔ کاربران پنل (ایمیل، نقش، تیک‌ها) — نقش c2 را ببین
- **بخش ۲**: نقش c2 را صندوق‌دار می‌کند
- **بخش ۳**: کنترل — باید `cashier` را نشان بدهد

بلافاصله با c2 تست کن: فقط منوهای پیش‌فرض صندوق‌دار (یا تیک‌های ذخیره‌شده)
دیده می‌شود و حسابداری با آدرس مستقیم به داشبورد برمی‌گردد.

> نکته: در بخش ۱ اگر کاربر دیگری هم اشتباهی owner شده، نقشش را همین‌جا با یک
> `update` مشابه اصلاح کن (ایمیلش را جایگزین کن).

## مرحلهٔ ۲ — کد (تغییر نقش از خودِ صفحهٔ دسترسی‌ها)

`patch-60c-role-edit.zip` را روی ریشهٔ پروژه Extract کن (Replace → بله):

| فایل | تغییر |
| --- | --- |
| `app/admin/access/AccessManager.tsx` | نقش هر کاربر در همین صفحه قابل تغییر است + هشدار مالک |
| `app/api/admin/access/route.ts` | تغییر نقش فقط با مالک (مدیر نمی‌تواند خودش را مالک کند) |

```powershell
git add -A
git commit -m "60c: edit role in access page (owner-only) + owner warning"
git push
```

از این به بعد: در صفحهٔ 🧩 دسترسی ماژول‌ها، کنار هر کاربر یک dropdown نقش هست
(مالک/مدیر/صندوق‌دار/کارمند). با تغییر نقش، تیک‌ها به پیش‌فرض همان نقش برمی‌گردند
و با «💾 ذخیره» ثبت می‌شود. روی کاربر مالک، برچسب «همه‌چیز باز — تیک‌ها روی مالک
اثری ندارند» می‌بینی تا دیگر این گره تکرار نشود.

## تست

1. بخش ۱ SQL: نقش c2 = owner؟ → بخش ۲ و ۳ → کنترل = cashier
2. ورود c2 → فقط منوهای مجاز؛ `/admin/accounting` دستی → برگشت به داشبورد
3. با مالک → صفحهٔ 🧩 → dropdown نقش c2 روی «صندوق‌دار» و ذخیره → درست بودن
4. با مدیر (اگر داری): dropdown نقش غیرفعال باشد (تغییر نقش فقط با مالک)
